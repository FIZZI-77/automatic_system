# Внутрикластерная capacity-кривая сервисов

Дата прогона: 2026-09-01  
Профиль: 15 параллельных read-сценариев, 2 реплики API Gateway, HPA зафиксирован 2/2  
Транспорт: k6 Job → Istio ingress → API Gateway → сервисы  
Ступень: 10 секунд warmup + 30 секунд measurement + 10 секунд stabilization

## Итог

Для 14 рабочих сценариев подтверждена стабильная граница не менее **420 полезных RPS**. На максимальной измеренной ступени все эти сценарии дали **0% HTTP-ошибок**, а худший p95 составил **101.07 ms** у Analytics.

Аппаратный предел не достигнут. Результат означает `capacity >= 420 RPS` для проверенного read-mix на текущем локальном кластере, но не доказывает, что 420 RPS является максимумом.

`Dispatch /dispatch/list` исключён из полезной кривой: он возвращал ошибку в 100% запросов на каждой ступени, включая минимальную. Это функциональный дефект endpoint, а не насыщение под нагрузкой.

Нелинейность p95 между соседними ступенями нормальна для коротких 30-секундных окон и фоновой активности локального кластера. Устойчивый рост заметен только на верхней точке, но SLO `p95 < 1 s` сохраняется с большим запасом.

## Ресурсы

На средней части прогона две реплики Gateway потребляли примерно 68–69 millicores CPU каждая. На верхних ступенях — примерно 157–163 millicores на Go-контейнер и около 264 millicores на каждый Istio sidecar. Память Gateway оставалась около 32–33 MiB на Go-контейнер и 49 MiB на sidecar.

Генератор в раннем снимке потреблял около 286 millicores и 647 MiB при лимите 2 CPU / 2 GiB; признаков насыщения генератора не было.

## Интерпретация

- Подтверждённая рабочая точка текущей конфигурации: **420 полезных RPS** при p95 ≤ 101.07 ms.
- Предварительный линейный ориентир для такого же read-mix: около **210 RPS на реплику Gateway**, но это не N+1-результат, потому что отдельный прогон с одной репликой не выполнялся.
- Для нахождения колена кривой следующий прогон нужно продолжить ступенями 35/40/50/60 RPS на сценарий, пока не появится рост ошибок, p95 выше выбранного SLO либо насыщение CPU/БД.
- Для честной кривой по железу нужны одинаковые прогоны минимум на 250m/500m/1000m/2000m CPU с неизменными данными и числом реплик. По одному resource point экстраполировать hardware curve нельзя.
