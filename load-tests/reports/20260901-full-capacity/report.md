# Отчёт по нагрузочному прогону 2026-09-01

## Условия

- Кластер: 3 Kubernetes-ноды, каждая по 20 CPU и примерно 15.5 GiB RAM.
- API Gateway: 2 реплики, request 25m CPU / 64Mi, limit 500m CPU / 512Mi на контейнер.
- Для финального baseline HPA зафиксирован в `minReplicas=2`, `maxReplicas=2`.
- Rate limiter обходился только для запросов с `X-Load-Test-Run-ID`; после теста штатный образ и limiter восстановлены.
- Ступень: 5 секунд прогрева, 20 секунд измерения, 5 секунд стабилизации.
- Нагрузка подавалась через `kubectl port-forward service/api-gateway`. Это годится для функциональной capacity-оценки, но не гарантирует равномерное распределение соединений между pod и не заменяет тест через ingress/load balancer.

## Подтверждённые нижние границы

| Сценарий | Максимальная проверенная нагрузка | Ошибки | p95 |
|---|---:|---:|---:|
| JWKS Gateway, 2 реплики | 100 RPS | 0% | 6.28 ms |
| Authenticated Gateway read | 50 RPS | 0% | 9.22 ms |
| Auth login | 10 RPS | 0% | 84.33 ms |
| Ticket read mix | 25 RPS | 0% | 20.93 ms |
| Dispatch preview | 10 RPS | 0% | 22.31 ms |
| Analytics query mix | 20 RPS | 0% | 25.69 ms |
| Full-system mixed | 20 RPS | 0% | 19.95 ms |

Это нижние границы, а не точки насыщения: на верхних ступенях перечисленных сценариев система в основном не достигла устойчивого роста latency или CPU saturation.

## Кривая RPS для API Gateway

Финальный JWKS-прогон с фиксированными двумя репликами:

| RPS | Ошибки | avg | p95 | p99 |
|---:|---:|---:|---:|---:|
| 25 | 0% | 94.17 ms | 676.14 ms | 917.69 ms |
| 50 | 0% | 5.30 ms | 6.78 ms | 8.14 ms |
| 100 | 0% | 2.38 ms* | 6.28 ms | 7.86 ms |

`*` Среднее и часть минимальных значений этого запуска повреждены скачком часов Docker Desktop: k6 зарегистрировал отрицательные значения в собственных `http_req_duration` и `http_req_sending`. p95/p99 верхних ступеней выглядят устойчиво, но 25 RPS содержит startup/clock выброс и требует повторения более длинной ступенью.

Линейную формулу «RPS на CPU» по этому прогону строить нельзя: ни Gateway, ни downstream не были доведены до насыщения, а снимок `kubectl top` сделан после сценариев, не на пике. Практический безопасный вывод сейчас: две реплики Gateway с лимитом 500m CPU каждая обслужили 100 RPS JWKS без ошибок и с p95 6.28 ms.

## Невалидные или пограничные сценарии

- `auth-refresh`: 100% ошибок уже на 1 RPS. Тест повторно использует один refresh token, хотя endpoint ротирует и отзывает его; это ошибка модели сценария, не capacity сервиса.
- `location`: 89.55–100% non-2xx. Генератор переиспользует пересекающиеся sequence/event данные между фазами; результаты нельзя использовать для capacity до исправления уникальности и классификации 409/validation errors.
- `ticket-read`: на 50 RPS было 0.899% ошибок и 9 EOF; 25 RPS прошли чисто. Возможный рабочий порог для этого короткого прогона находится между 25 и 50 RPS.
- `analytics`: одна ошибка на ступени 10 RPS, при этом 20 RPS прошли без ошибок. Это одиночный transport/runtime выброс, а не монотонное насыщение.
- `dispatch-preview`: четыре dropped iterations и длинный выброс на начальной ступени 2 RPS; 5 и 10 RPS стабильны.

## Ресурсы во время снимка

На снимке после suite основные потребители были инфраструктурными: ClickHouse около 297m CPU / 925Mi, Kafka-брокеры около 275–294m CPU и 618–701Mi каждый, Elasticsearch около 22m CPU / 1276Mi. Gateway на двух pod использовал примерно 1–14m CPU и 17–27Mi памяти на контейнер плюс Istio sidecar. Снимок подтверждает большой запас Gateway, но не является peak sampling.

## Что нужно для точной hardware-кривой

1. Запускать k6 внутри Kubernetes либо через ingress, чтобы Service реально балансировал соединения.
2. Зафиксировать HPA и последовательно проверить одинаковый сценарий при лимитах 250m, 500m и 1000m CPU.
3. Использовать ступени минимум 2–3 минуты и снимать Prometheus range-метрики CPU, memory, throttling, latency и Kafka lag на каждой ступени.
4. Увеличивать RPS до первой устойчивой точки: error rate > 0.1%, p95 выше SLO, CPU throttling либо рост backlog.
5. Исправить refresh/location сценарии и повторить ticket-read в диапазоне 30–50 RPS меньшим шагом.
