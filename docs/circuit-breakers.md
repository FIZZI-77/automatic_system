# Circuit breaker для Brigade и Dispatch

Защищены четыре зависимости: Brigade → Department/Profile и Dispatch →
Location/Routing. У каждой связи отдельный breaker на gRPC-соединение;
все unary RPC одного поставщика разделяют состояние, включая Profile-проверку
ведомства диспетчера во входящем interceptor Brigade.

Используется `github.com/sony/gobreaker/v2 v2.3.0`. Модули содержат небольшие
адаптеры `pkg/grpcbreaker`, чтобы каждый сервис по-прежнему собирался независимо
из своего Docker-контекста без локальных межмодульных replace-зависимостей.

Настройки обоих сервисов в `config.yaml` (переменные окружения приоритетнее):

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| `CIRCUIT_BREAKER_FAILURE_THRESHOLD` | `5` | Последовательных сбоев до открытия |
| `CIRCUIT_BREAKER_INTERVAL` | `30s` | Фиксированное окно сброса счётчиков |
| `CIRCUIT_BREAKER_OPEN_TIMEOUT` | `60s` | Пауза до одного пробного вызова |
| `CIRCUIT_BREAKER_CALL_TIMEOUT` | `2s` | Верхняя граница длительности вызова |

Неверные значения останавливают запуск с ошибкой конфигурации.
Окно фиксированное, не скользящее. Half-open пропускает один вызов одновременно:
успех закрывает цепь, сбой доступности открывает её повторно.

В сбои входят gRPC `Unavailable`, `DeadlineExceeded` и `ResourceExhausted`.
Ошибки валидации, прав и отсутствия записи считаются ответами работающего сервиса.
Отмена/истечение родительского контекста не считается сбоем поставщика;
уже отменённый запрос не доходит до сети. Более короткий дедлайн родителя
сохраняется; длительный ограничивается настройкой вызова.
Открытая цепь и занятый пробный вызов дают gRPC `Unavailable` сразу, а локально
распознаются через `errors.Is(err, grpcbreaker.ErrRejected)`.
Brigade прекращает свои повторы Department при таком локальном отказе.
Смены состояния пишутся в структурированный журнал с именем зависимости.

## Поведение при отказах

- Department/Profile: операции, требующие проверок, возвращают недоступность.
  Положительные ответы из устаревшего кэша для проверки прав не используются.
- Location: отсутствие свежих координат останавливает подбор/подтверждение,
  после порога ошибок — без сетевого ожидания.
- Routing: подбор при ошибке доступности сортирует подходящие бригады
  по расстоянию по прямой, с детерминированным порядком при равенстве.
  `eta_seconds=-1` означает неизвестное ETA. `reachable=true` в этом режиме
  разрешает попытку автоматического назначения и не подтверждает наличие дорожного
  маршрута. Бизнес-проверка бригады повторяется перед резервированием.
- Если Routing недоступен при создании маршрута **автоматического** назначения,
  Dispatch сохраняет `CONFIRMING` с `route_id=NULL` и событием
  `dispatch.routing_degraded`, затем назначает бригаду заявке. После перезапуска
  тот же процесс продолжается из базы. Ошибка назначения освобождает резерв
  через существующий механизм компенсаций. Успешный `dispatch.assigned` содержит
  `routing_degraded=true`. Маршрут задним числом автоматически не создаётся.
- Ручное подтверждение продолжает требовать маршрут. Отмена запроса,
  ошибки прав/валидации и пустой успешный ответ Routing не запускают деградацию.

Breaker не добавляет повторы изменяющих RPC и не ограничивает количество
одновременных вызовов в Closed. Первые запросы во время отказа ограничены таймаутом.

## Проверки

```powershell
go test ./Brigade_Service/pkg/grpcbreaker ./Dispatch_Service/pkg/grpcbreaker ./Brigade_Service/src/core/service ./Dispatch_Service/src/core/service
```

Тесты переходов и дедлайнов используют `testing/synctest` без реальных ожиданий.
PostgreSQL-тесты деградации и восстановления автоматически входят в существующую
CI-проверку `workflow-recovery-integration` для Dispatch. Локально задайте
`RECOVERY_TEST_DATABASE_URL` на отдельную тестовую базу и запустите
`go test -race -count=1 ./Dispatch_Service/src/core/service`.
