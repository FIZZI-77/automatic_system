# Automatic City Services

Automatic City Services -- система для работы с городскими обращениями от
сообщения жителя о проблеме до назначения бригады и фиксации результата.
Она объединяет заявки, сотрудников и подразделения, бригады и транспорт,
объекты инфраструктуры, маршруты и контроль сроков. Житель, работник,
диспетчер и администратор видят разные рабочие разделы одного веб-приложения;
доступ к действиям определяется учетной записью и проверками на сервере.

Система состоит из веб-интерфейса, внешнего HTTP-шлюза и отдельных Go-сервисов.
Шлюз передает предметные запросы внутренним сервисам по gRPC. Для операций,
которые должны завершиться вместе с запросом, сервисы обращаются друг к другу
напрямую; для последующей независимой обработки изменений используют события
Kafka. Данные разделены по предметным областям: заявка, координаты, файл и
аналитическая запись имеют разных владельцев и разные задачи хранения.
Серверные маршруты веб-приложения также обращаются к геокодированию, данным
карты и Valhalla напрямую, минуя шлюз.

Этот README служит точкой входа. Подробности о моделях, функциях и таблицах БД
находятся в документации каждого сервиса, а развертывание и эксплуатация
описаны в [разделе Kubernetes](k8s/README.md).

## Как устроена система

![Прямые связи, подтвержденные кодом](docs/architecture/sync-interactions.svg)

![Публикация и чтение событий Kafka](docs/architecture/event-interactions.svg)

Полная [карта взаимодействий с доказательствами в коде](docs/architecture/code-interactions.md)
поясняет каждую группу связей, состав тем и границы проверки.

1. [Веб-интерфейс](Frontend/README.md) отправляет предметные запросы в
   [API Gateway](API_Gateway/README.md). Шлюз проверяет доступ и передает вызов
   нужному сервису по gRPC.
2. Сервисы владеют своими предметными данными. Заявки, бригады, городские
   объекты и учетные записи не хранятся в общей прикладной таблице. Основное
   хранилище сервисов: PostgreSQL. Геоданные используют PostGIS, оперативные
   координаты хранятся в Redis, файлы размещаются в S3-совместимом хранилище.
3. Для действий, требующих ответа сразу, сервисы вызывают друг друга по gRPC.
   [Dispatch Service](Dispatch_Service/README.md), например, обращается к
   заявкам, бригадам, координатам и маршрутам при назначении исполнителей.
4. Изменения части предметных данных публикуются как события через Kafka.
   Большинство издателей используют таблицы исходящих сообщений; Location
   передает координаты из Redis Stream. Получатели независимо обновляют сроки,
   уведомления, журнал действий и аналитические представления. Наличие темы в
   конфигурации само по себе не означает, что для нее есть издатель в коде.
5. Инфраструктура запускается в Kubernetes. Манифесты, выпуск приложений,
   наблюдаемость и порядок восстановления описаны в
   [документации кластера](k8s/README.md).

Подробные схемы и источники находятся в
[архитектурном разделе](docs/architecture/README.md). Они описывают код
репозитория, но не подтверждают состояние запущенного кластера.

## Назначение и возможности

Основной предмет системы -- городская заявка. Ее можно создать, просмотреть,
связать с объектом инфраструктуры, назначить исполнителям и провести через
состояния выполнения. Вокруг заявки работают отдельные процессы: расчет
сроков реакции и выполнения, доставка уведомлений, запись действий и подготовка
аналитических данных. Каждый из них получает необходимые данные через вызовы
или события, а не хранит вторую «главную» карточку заявки.

Веб-приложение открывает рабочие разделы по роли пользователя:

- **Житель** видит свои заявки, создает обращение, получает уведомления и
  управляет профилем.
- **Работник** видит задания своей смены, маршрут, отчеты и профиль.
- **Диспетчер** работает с инцидентами и бригадами на карте, назначениями,
  сроками, операциями и отчетами.
- **Администратор** видит показатели, структуру подразделений и бригад,
  объекты инфраструктуры, справочники, аналитику, аудит и управление.

Карта объединяет заявки и передаваемые транспортом координаты; Routing Service
строит и хранит маршруты, используя Valhalla для дорожного расчета. File Service
выдает ссылки для загрузки вложений в объектное хранилище, а Report Service
формирует документы и выгрузки. Конкретная доступность раздела, действие и
состав ответа зависят от роли, данных и состояния связанных сервисов.

Этот обзор перечисляет реализованные в коде маршруты, обработчики и связи.
Он не означает, что любой внешний источник данных, канал доставки или контур
развертывания доступен без отдельной настройки и проверки. Подробное
сопоставление экранов и серверных операций находится в
[карте возможностей](docs/frontend-backend-coverage.md).

## Путь заявки

1. Пользователь входит через [Auth Service](Auth_Service/README.md), затем
   создает заявку через шлюз. [Ticket Service](Ticket_Service/README.md) хранит
   ее карточку, состояние и историю. Заявка может быть связана с объектом из
   [Asset Service](Asset_Service/README.md).
2. [Dispatch Service](Dispatch_Service/README.md) подбирает бригаду автоматически
   либо принимает ручной выбор диспетчера. Он использует данные
   [Brigade Service](Brigade_Service/README.md), свежие координаты из
   [Location Service](Location_Service/README.md) и оценку поездки из
   [Routing Service](Routing_Service/README.md). После резервирования и
   подтверждения назначения обновляются заявка и маршрут.
3. Работник меняет состояние заявки и добавляет сведения о выполнении. Файлы
   загружаются через [File Service](File_Service/README.md). Формирование
   документа о выполненных работах и аналитических выгрузок относится к
   [Report Service](Report_Service/README.md).
4. События заявки обрабатывают [SLA Service](SLA_Service/README.md),
   [Notification Service](Notification_Service/README.md),
   [Audit Service](Audit_Service/README.md) и
   [Analytics Service](Analytics_Service/README.md). Это отдельные потребители:
   они не подменяют источник истины о состоянии заявки.

Конкретные переходы состояний, проверки прав и обработка ошибок описаны в
README соответствующих сервисов. Сопоставление экранов и операций шлюза есть в
[карте веб-интерфейса и серверных возможностей](docs/frontend-backend-coverage.md).

## Стек проекта

| Область | Технологии | Для чего используются |
|---|---|---|
| Веб-приложение | React, TypeScript, Vinext/Vite, Leaflet | Ролевые рабочие разделы, формы и интерактивная карта. |
| Серверные приложения | Go, HTTP, gRPC | Внешние запросы через API Gateway и прямые вызовы между предметными сервисами. |
| Основные данные | PostgreSQL; PostGIS для пространственных данных | Состояние сервисов, заявки, объекты и геозоны. |
| Отказоустойчивое хранение | Patroni с координацией через Kubernetes API, Citus, PgBouncer в контурах высокой доступности | Переключение групп PostgreSQL, распределение таблиц Ticket по `department_id` и соединения с базами. |
| События и оперативные данные | Kafka, Redis и Redis Streams | Независимая обработка изменений, быстрый доступ к текущим координатам и передача их событий. |
| Аналитика | ClickHouse | Хранение и чтение аналитических представлений событий. |
| Файлы и дороги | MinIO (S3-совместимое хранилище), Valhalla | Вложения и сформированные документы; расчет дорожных маршрутов. |
| Уведомления | Redis, SMTP, Firebase Cloud Messaging при настройке ключей | Живые уведомления, электронная почта и браузерные push-уведомления. |
| Запуск и сеть | Kubernetes, Helm, Kustomize, Istio, ngrok для локальной публичной ссылки | Размещение сервисов, настройка входящего трафика и внутренних соединений. |
| Доставка изменений | GitHub Actions, GHCR, Flux, Flagger | Проверки и сборка образов, согласование состояния кластера и канареечное продвижение там, где оно включено. |
| Наблюдаемость | Prometheus, Grafana, OpenTelemetry, Jaeger, Filebeat, Elasticsearch, Kibana | Метрики и панели, распределенные трассировки, сбор и поиск журналов. |

Состав и режим работы инфраструктуры различаются между `local`, `local-ha`,
`dev` и `prod`. Источник точных условий запуска и выпуска --
[документация Kubernetes](k8s/README.md) и [рабочий процесс CI/CD](.github/workflows/ci.yml).
